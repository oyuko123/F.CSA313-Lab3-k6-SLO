## 2. SLO тодорхойлолт

Сценарио бүрийн хэмжүүрийг хэмжигдэхүйц SLO болгон тодорхойлов.

| Сценарио | SLI | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | `/cart/add` latency | p95 < 50 мс | 20 VU тогтмол ачаалал, 1 минут |
| Reliability | `/pay` error rate | < 8% | 20 VU, 1 минут |
| Availability | Нийт хүсэлтийн амжилтын хувь | ≥ 90% | 20 VU, 2 минут, 10 секундийн зогсолт |
| Additional Performance | `/report` latency | p95 < 450 мс | 20 VU, 1 минут |

### Босго сонгосон үндэслэл

- **Performance:** `/cart/add` нь локал сервер дээр маш хурдан хариулах endpoint тул 200 мс-ийн жишээ босгоос илүү нарийн 50 мс-ийн p95 босго сонгосон.
- **Reliability:** `/pay` endpoint-д ойролцоогоор 5%-ийн зориудаар үүсгэсэн алдаа байдаг тул санамсаргүй хэлбэлзлийг тооцож 8%-ийн error rate босго сонгосон.
- **Availability:** Серверийн тасалдлын үед нийт хүсэлтийн 90%-иас дээш нь амжилттай байх шаардлагатай гэж үзэж, 90%-ийн босго сонгосон.
- **Additional Performance:** `/report` нь боловсруулах хугацаа харьцангуй урт endpoint тул хэрэглэгчийн хүлээлгийн хугацааг хэт ихэсгэхгүй байхаар p95 latency-ийн босгыг 450 мс гэж сонгосон.

### Availability Error Budget

Availability SLO нь 90%, тестийн цонх нь 2 минут буюу 120 секунд.

```text
Error budget = 120 × (1 - 0.90)
             = 12 секунд

```

## 3. k6 тестийн үр дүн

### 3.1 PASS тест

1 минутын турш 20 VU тогтмол ачааллаар ажиллуулсан тестэд бүх threshold PASS болсон.

| Хэмжүүр | Бодит үр дүн | Threshold | Үр дүн |
|---|---:|---:|---|
| `/cart/add` p95 latency | 2.66 мс | p95 < 50 мс | PASS |
| `/report` p95 latency | 390.24 мс | p95 < 450 мс | PASS |
| `/pay` error rate | 4.72% | < 8% | PASS |
| Checks / availability | 98.42% | > 90% | PASS |

PASS тестийн бүрэн гаралт `results/pass.txt` файлд хадгалагдсан.

### 3.2 Chaos тест

2 минутын тестийн явцад серверийг зориудаар ойролцоогоор 10 секунд зогсоож, дараа нь дахин ажиллуулсан.

| Хэмжүүр | Бодит үр дүн | Threshold | Үр дүн |
|---|---:|---:|---|
| `/cart/add` p95 latency | 2.60 мс | p95 < 50 мс | PASS |
| `/report` p95 latency | 390.31 мс | p95 < 450 мс | PASS |
| `/pay` error rate | 20.02% | < 8% | FAIL |
| Checks / availability | 82.89% | > 90% | FAIL |

Chaos тестийн үед нийт 5754 HTTP хүсэлт илгээгдсэнээс 984 check амжилтгүй болсон. Үүний улмаас checks-ийн хувь 82.89% болж, availability SLO-ийн 90%-ийн босго хангагдаагүй.

### 3.3 Error budget-ийн шинжилгээ

2 минутын хугацааны SLO-ийн 90%-ийн availability нь 10%-ийн error budget гэсэн үг. Иймээс хугацаагаар тооцвол:

```text
120 секунд × 10% = 12 секунд

```

Туршилтын үед серверийг ойролцоогоор 10 секунд зогсоосон нь 12 секундын хугацааны error budget-ээс бага байсан. Гэвч k6-ийн checks нь хугацаагаар бус хүсэлтийн тоогоор тооцогддог. Сервер зогссон үед 20 VU-ийн илгээсэн хүсэлтүүд connection failure болж хурдан буцсан тул богино хугацаанд олон хүсэлт амжилтгүй болсон. Иймээс хугацааны budget-ийг хэтрээгүй боловч хүсэлтийн түвшний availability 82.89% болж, 90%-ийн SLO-г хангаагүй.

### 3.4 Reliability ба Availability-ийн хамаарал

Chaos тестийн үед серверийн тасалдал нь `/pay` endpoint-д мөн нөлөөлж, error rate 20.02% болсон. Ингэснээр reliability-ийн 8%-ийн threshold FAIL болсон. Availability нь бүх endpoint-ийн хүсэлтүүд амжилттай үйлчилсэн эсэхийг нийтэд нь хэмждэг бол reliability нь тодорхой үйлдэл, тухайлбал `/pay` төлбөрийн хүсэлтийн алдааны давтамжийг хэмждэг. Иймээс availability болон reliability нь хоорондоо холбоотой боловч тусдаа SLI юм.

## 4. Threshold зориуд FAIL болгох туршилт

`/report` endpoint-ийн threshold-ийг зориудаар хэт хатуу болгож `p(95)<100 мс` болгон туршсан. Серверийн `/report` endpoint нь 200–400 мс хооронд санамсаргүй хүлээлттэй тул уг threshold хангагдахгүй.

| Хэмжүүр | Бодит үр дүн | Threshold | Үр дүн |
|---|---:|---:|---|
| `/cart/add` p95 latency | 2.41 мс | p95 < 50 мс | PASS |
| `/report` p95 latency | 390.61 мс | p95 < 100 мс | FAIL |
| `/pay` error rate | 4.87% | < 8% | PASS |
| Checks / availability | 98.37% | > 90% | PASS |

k6 нь `/report`-ийн threshold зөрчигдсөнийг илрүүлж, `exit=99` гэсэн non-zero exit code буцаасан. Энэ нь threshold failure гарсан үед CI pipeline build-ийг амжилтгүй болгоход ашиглаж болохыг харуулж байна.

FAIL тестийн бүрэн гаралт `results/fail.txt` файлд хадгалагдсан.
